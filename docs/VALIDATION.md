测试使用本地模拟数据，不会调用 Vertex。CI 配置在 Linux、Windows 和 macOS 上分别运行 Node.js 22、24，并在 Linux 上额外运行最低支持版本 22.9.0；每个任务限时 15 分钟。实际运行结果以仓库的 [Actions](https://github.com/ken050210/vertex-streaming-anti-truncation/actions) 为准。

独立启动入口也已在 Windows / Node.js 24.16.0 上检查：健康接口返回 200，未鉴权的模型请求返回 401，鉴权后模型列表正确，监听地址为本机回环地址。该检查使用虚拟凭据，没有发送模型请求。

## 独立网关 0.3.1 的真实请求

2026-09-22，在 Windows / Node.js 24.16.0 上使用临时回环实例和内存中的服务账号凭据，对 Gemini 3.8 Flash 发送三条固定文本请求，每条最多 512 个输出 token：

- Standard 普通非流式回复：HTTP 200、非空正文和 `stop`。
- Standard 流式抗截断：HTTP 200，原生参数流，454 个正文字符分 7 次读取到达，跨度 610 ms；`restored: true`、`stop`、`[DONE]`，实际档位 `ON_DEMAND`。
- Flex 原生严格 Schema：HTTP 200，输出符合封闭对象约束；未指定 `items` 的数组保留了 `null` 和嵌套数组，结束原因为 `stop`，实际档位 `ON_DEMAND_FLEX`。

三条请求的编号均与日志对应，`responseIntegrity.outcome` 都为 `complete`。测试未写入日常配置，临时监听已关闭。真实 Express、Priority、其他模型、Google 目录权限与 SillyTavern 界面不在本轮验收范围。

## 提取前的真实请求

2026-09-20，原 router 集成对同一流式传输核心运行了两条固定文本请求，各限制 512 个输出 token。非流式和流式均返回 HTTP 200、已还原正文和 `stop`。流式请求记录到 7 次带正文的读取，正文到达跨度为 911 ms，并收到 `[DONE]`。这些记录说明当时的 Vertex 请求确实分段到达。

上述历史结果来自原 router 集成，不能替代独立网关测试；0.3.1 的独立真实请求见上一节。默认 `npm run verify` 始终只使用本地模拟数据。服务的健康检查只说明进程可访问。

## 在自己的环境验收

完成 README 中的设置并启动服务后，运行：

```sh
npm run smoke -- --live
```

该命令会发送两条客户端请求，每次最多 512 个输出 token；开启提示词重试时最多提交 4 次上游请求，重试额外包含自定义文本。它检查普通回复的还原状态，以及流式回复的非空正文、`stop`、`[DONE]` 和还原标志；还要求至少两次带正文的读取，时间跨度至少 100 ms。最后用响应中的 `x-request-id` 核对 `/admin/events`。图片输入开启时，命令在发送任何请求前停止，因为图片请求走缓冲回退，无法通过流式检查。

验收日志只包含元数据。输出片段的到达次数受模型、网络和缓冲行为影响，单次结果不能保证每一条回复都以相同速度分段。

## 尚未证明的效果

短请求和模拟测试不能证明长篇内容不会截断。网关无法恢复模型未生成或网络未收到的内容。模型也可能直接返回普通文本，此时日志会显示 `restored: false`。

当前支持保存多个 Gemini 模型，不代表这些模型都已经过真实推理验收。没有为其他服务商、远程公开部署或不同客户端做兼容性保证。
